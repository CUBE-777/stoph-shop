# Stoph Shop — المرحلة 1 (MVP)

متجر مغربي: React + Vite + Supabase (قاعدة البيانات، المصادقة، تخزين الصور) + Netlify.
الدفع عند الاستلام فقط. عربي (RTL) وفرنسي (LTR)، وضع داكن افتراضي.

## ما تم اختباره فعلاً وما لم يُختبر

**اختُبر فعلاً (في بيئة البناء):**
- `npm test` (نسخة المرحلة 1): 8 اختبارات للمنطق المشترك في `src/lib/shop.js` (تطبيع الهاتف، الأسعار والخصم، قواعد التوفر، التحقق من النموذج، السلة، رسوم التوصيل، انتقالات حالة الطلب) — **نجحت كلها**.
- فحص صياغة (syntax) كل ملفات JS/JSX عبر TypeScript — دون أخطاء.
- تطابق مفاتيح الترجمة بين العربية والفرنسية (209 مفتاحاً في كل لغة).

**لم يُختبر (لأن البيئة بلا إنترنت ولا PostgreSQL):**
- `npm install` و`npm run build` و`npm run dev`: لم تُشغَّل، فقد يظهر خطأ بسيط عند أول تشغيل.
- ملفات SQL لم تُنفَّذ على قاعدة بيانات حقيقية. اختبارات قاعدة البيانات جاهزة في `tests/db/db_tests.sql` ويجب تشغيلها يدوياً (انظر الخطوة 7).
- الاتصال بـ Supabase، رفع الصور، تسجيل دخول المدير، النشر على Netlify: يحتاجون إعدادك أنت.
- لم يُراجَع الشكل البصري على متصفح أو هاتف.

## 1) إعداد Supabase
1. أنشئ مشروعاً جديداً في supabase.com (اختر منطقة قريبة، مثل أوروبا).
2. افتح **SQL Editor** ونفّذ الملفات بهذا الترتيب (كل ملف كاملاً):
   `supabase/01_schema.sql` ← `02_rls_storage.sql` ← `03_functions.sql`
3. من **Project Settings → API** انسخ: `Project URL` و`anon public key`.
   لا تستخدم مفتاح `service_role` في هذا المشروع إطلاقاً.

## 2) أول مدير (آمن، دون كلمة مرور في الكود)
1. **Authentication → Users → Add user → Create new user**: بريدك وكلمة مرور قوية تختارها أنت.
2. **Authentication → Sign In / Providers**: عطّل **Allow new users to sign up**.
3. افتح `supabase/04_first_admin.sql`، بدّل `CHANGE-ME@example.com` ببريدك، ونفّذه مرة واحدة.
   الدالة ترفض العمل إذا وُجد مالك سابق، ولا يمكن استدعاؤها من المتصفح.

حتى لو سُجّل مستخدم غريب، لن يملك صلاحيات: كل سياسات RLS تتحقق من `staff_profiles` والأدوار.

## 3) التشغيل المحلي (VS Code + PowerShell)
```powershell
cd stoph-shop
npm install
Copy-Item .env.example .env.local
# عدّل .env.local وضع VITE_SUPABASE_URL و VITE_SUPABASE_ANON_KEY
npm run dev
```
المتجر: http://localhost:5173 — الإدارة: http://localhost:5173/admin

## 4) النشر على Netlify
1. ادفع المشروع إلى GitHub (`.env.local` مستثنى تلقائياً عبر `.gitignore`).
2. Netlify → **Add new site → Import from Git** (الإعدادات تُقرأ من `netlify.toml`).
3. **Site configuration → Environment variables**: أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`
   (واختيارياً `VITE_CONTACT_PHONE` و`VITE_CONTACT_WHATSAPP` و`VITE_CONTACT_EMAIL` و`VITE_LOGO_URL`).
4. أعد النشر. في Supabase: **Authentication → URL Configuration** أضف رابط موقعك.

## 5) قبل الإطلاق (مهم)
- من `/admin/shipping` عدّل **السعر الافتراضي**: القيمة 40 درهماً مجرد قيمة مؤقتة وضعتُها أنا.
- نصوص صفحة التوصيل والسياسات مسودة عامة؛ سياسة الإرجاع غير مكتوبة بعد. راجعها قانونياً.
- أضف تصنيفاتك ومنتجاتك وصورك الحقيقية من `/admin`.

## 6) بيانات تجريبية (اختيارية، للتطوير فقط)
نفّذ `supabase/05_seed_demo_optional.sql`. كل صفوفها تبدأ بـ `demo-` ويوجد سطر حذف في آخر الملف.

## 7) الاختبارات
- منطق الواجهة: `npm test`.
- قاعدة البيانات: الصق `tests/db/db_tests.sql` في SQL Editor ونفّذه على مشروع تطوير. يعمل داخل معاملة تنتهي بـ `ROLLBACK`
  (لا يترك شيئاً)، ويفحص: حساب الأسعار والخصم والتوصيل على الخادم، لقطة الطلب، رفض المتغير/المنتج غير المتاح أو المخفي،
  رفض الكمية والهاتف غير الصحيحين، عدم إنشاء طلبات جزئية، ومنع الزائر والمستخدم غير الموظف من قراءة الطلبات أو تغيير حالتها.
  رسالة النجاح: `ALL DB TESTS PASSED`.

## بنية المشروع
```
supabase/   ملفات SQL (جداول، RLS، دوال create_order / set_order_status، أول مدير، بيانات تجريبية)
src/lib/    shop.js (منطق خالص مُختبَر)، supabase.js، hooks.js
src/services/  catalog.js (المتجر) و admin.js (الإدارة): كل عمليات قاعدة البيانات هنا فقط
src/context/   اللغة/المظهر، السلة
src/pages/, src/components/, src/admin/   الواجهات
src/i18n/dictionary.js   كل النصوص بالعربية والفرنسية
src/styles.css   كل الألوان والمسافات كمتغيرات CSS
```
استبدال الشعار: عدّل مكوّن `Logo` في `src/components/ui.jsx` أو اضبط `VITE_LOGO_URL`.

## قرارات وحدود معروفة
- **الأمان:** الطلب يُنشأ فقط عبر `create_order` (يحسب الأسعار والتوصيل ويتحقق من التوفر ذرّياً). المتصفح لا يرسل أي سعر.
  الزائر لا يملك أي صلاحية على الطلبات والزبائن. تغيير الحالة فقط عبر `set_order_status` بانتقالات محددة.
- **لا حماية من الإغراق (spam):** أي شخص يستطيع استدعاء `create_order`. أضف لاحقاً CAPTCHA أو Edge Function مع تحديد معدل.
- **جدول الزبائن:** يُحدَّث الاسم عند تكرار نفس رقم الهاتف؛ الطلب نفسه يحفظ لقطة ثابتة لا تتأثر.
- **حفظ المنتج في الإدارة:** المنتج والمتغيرات والصور تُحفظ بطلبات متتالية وليست معاملة واحدة؛ عند فشل خطوة تبقى السابقة محفوظة وتظهر رسالة خطأ.
- **لم أنفّذ** لوحة جانبية للسلة (صفحة السلة تكفي للـ MVP)، ولا نموذج رسائل في صفحة التواصل (لا يوجد خادم لاستقباله؛ تُعرض بيانات التواصل من متغيرات البيئة).
- الأدوار والصلاحيات موجودة في قاعدة البيانات (`owner`, `manager`) وتُطبَّق على كل شاشة، لكن واجهة إدارة الموظفين مؤجلة للمرحلة 2.

# المرحلة 2 — إدارة التجارة والعمليات

## ما أُضيف
- **الزبائن:** توحيد صيغة الهاتف (+212 / 00212 / 06…) على الخادم؛ الزبون = (الهاتف + الاسم)، فلا تُدمج أسرة تشترك في رقم؛ صفحة سجل طلبات الزبون؛ ملاحظات داخلية.
- **الطلبات:** حالات `new, pending_confirmation, confirmed, preparing, shipped, delivered, cancelled, returned`؛ جدول `order_status_history` (السابقة/الجديدة/الموظف/الوقت/الملاحظة)؛ جدول `order_transitions` يحدد الانتقال والصلاحية المطلوبة؛ بحث وفلاتر (رقم، حالة، تاريخ، مدينة، هاتف).
- **التتبع العام `/track`:** رمز عشوائي `SS-XXXXXXXXXX` + رقم الهاتف، عبر دالة `track_order` فقط (لا قراءة مباشرة لـ `orders`). لا عنوان ولا اسم؛ فقط الحالة والمنتجات والمجموع ومراحل الطلب. المحاولات الخاطئة تُسجَّل وتُحجب (8 فاشلة/15 دقيقة لكل رمز أو هاتف، 10 لكل IP).
- **الكوبونات والتخفيضات:** كوبون نسبة أو مبلغ ثابت، تاريخ بداية/نهاية، حد أدنى، سقف للخصم، أقصى استعمال، مرة لكل هاتف، تفعيل/تعطيل. كل الشروط تُفحص في `_price_order` على الخادم، والخصم الفعلي يُخزَّن في الطلب (`coupon_discount`, `coupon_code`). الخصم لا يتجاوز مجموع المنتجات. تخفيض المنتج له نافذة زمنية اختيارية.
- **الصلاحيات (RBAC):** `products.view/create/update/delete`, `categories.manage`, `orders.view`, `orders.update_status`, `orders.cancel`, `customers.view/update`, `shipping.manage`, `coupons.manage`, `reports.view`, `staff.manage`, `settings.manage`, `audit.view`. أدوار جاهزة: `owner`, `manager`, `support`. صفحة `/admin/staff` لإضافة الموظفين وتحديد أدوارهم وتعديل صلاحيات الأدوار (للمالك فقط).
- **الإشعارات وواتساب:** شريط تنبيه في لوحة الإدارة عند وصول طلبات جديدة (استطلاع كل 30 ثانية وعنوان التبويب `(n)`)، وزر **يفتح** محادثة واتساب برسالة جاهزة ويُرسلها المدير **يدوياً**. لا API ولا إرسال آلي.
- **التقارير `/admin/reports`:** الطلبات حسب الحالة، المبيعات (المسلّمة فقط)، الملغاة والمرتجعة منفصلتان، أكثر المنتجات طلباً، حسب المدينة وحسب اليوم. الفترة حسب تاريخ **إنشاء** الطلب بتوقيت الدار البيضاء.
- **التدقيق:** `audit_logs` للإلحاق فقط (trigger يمنع التعديل والحذف حتى على مالك قاعدة البيانات، وصلاحيات الكتابة مسحوبة من الموظفين). يُسجَّل: المنتجات والأسعار، المتغيرات، التوصيل، الكوبونات، الأدوار والصلاحيات والموظفون، الزبائن، حالات الطلبات. صفحة `/admin/audit`.
- **إنشاء الطلب:** حماية من الإغراق (5 طلبات/ساعة لكل هاتف، 20/ساعة لكل IP) وتحديد محاولات تخمين الكوبونات.

## التطبيق (ترتيب إلزامي، على نسخة احتياطية أولاً)
1. **خذ نسخة احتياطية** (Supabase → Database → Backups) أو جرّب أولاً على مشروع تطوير.
2. في SQL Editor نفّذ بالترتيب، كل ملف كاملاً: `06_phase2_schema.sql` ← `07_phase2_security.sql` ← `08_phase2_orders.sql` ← `09_phase2_reports.sql`.
   كل ملف معاملة واحدة: عند أي خطأ لا يُطبَّق شيء ويمكنك إعادة التشغيل. **لا تعد تنفيذ `03_functions.sql`** بعد المرحلة 2 (سيعيد الدوال القديمة).
3. بياناتك الحالية تبقى: الأذونات القديمة أُعيدت تسميتها (`roles.manage→staff.manage`, `orders.manage→orders.update_status`, `products.manage→products.update`) فيحتفظ المالك بكل شيء؛ الطلبات القديمة تحصل على رمز تتبع وسجل حالة أولي (تقريبي).
4. انشر الواجهة الجديدة (ادفع إلى GitHub ← Netlify). **لا متغيرات بيئة جديدة.**
5. اختياري — دعوة الموظفين بالبريد من لوحة الإدارة: انشر الدالة `supabase/functions/invite-staff` (`supabase functions deploy invite-staff`). بدونها: ادعُ الشخص من Supabase ← Authentication ← Users ← Invite user، ثم أضفه في `/admin/staff`. الموظف المدعو يضبط كلمة مروره من الإعدادات.

## الاختبارات
- `npm test`: 13 اختباراً للمنطق المشترك (نافذة التخفيض، الانتقالات حسب الدور، رسالة واتساب، رمز التتبع…) — **نجحت كلها** في بيئة البناء.
- `tests/db/db_tests.sql` (المرحلة 1) و`tests/db/db_tests_phase2.sql` (المرحلة 2): شغّلهما في SQL Editor على مشروع تطوير؛ يعملان داخل معاملة تنتهي بـ ROLLBACK. تغطي المرحلة 2: توحيد الهاتف وفصل أفراد الأسرة، نافذة التخفيض، كوبونات (نسبة/ثابت/سقف/حد أدنى/منتهٍ/معطّل/مستنفد/مرة لكل هاتف)، تجاهل أي سعر قادم من المتصفح، التتبع الصحيح والخاطئ وعدم تسريب العنوان/الاسم، الحجب بعد محاولات التخمين، حد الطلبات، منع الزائر من الجداول والدوال الإدارية، دور support (يؤكد ولا يلغي ولا يرى التقارير)، منع منح النفس صلاحيات، حماية آخر مالك، وعدم قابلية سجل التدقيق للتعديل أو الحذف.

## ما لم يُختبر فعلاً (مهم)
- **لم يُنفَّذ أي SQL** (لا PostgreSQL في بيئة البناء): ملفات 06–09 واختباراتها غير مُشغَّلة. توقّع احتمال وجود خطأ بسيط عند أول تنفيذ؛ الاختبارات مصمَّمة لكشفه. اختبار الموظفين يُدخل مستخدمين وهميين في `auth.users` مباشرة وقد تحتاج أعمدة إضافية في إصدارك من Supabase.
- الواجهة لم تُبنَ ولم تُفتح في متصفح (`npm run build` لم يُشغَّل)؛ فُحصت الصياغة وتطابق الاستيراد/التصدير فقط.
- Edge Function `invite-staff` غير منشورة وغير مختبرة.
- تحديد المعدل حسب IP يعتمد على ترويسات الوكيل (best effort)؛ الحماية الأقوى هي حسب الهاتف والرمز. نتيجة جانبية: من يعرف هاتفك قد يحجب تتبعك مؤقتاً (15 دقيقة) بمحاولات خاطئة.

## قرارات تحتاج موافقتك
- **حالة `new`:** الطلبات الجديدة ما زالت تبدأ بـ `pending_confirmation` (للحفاظ على سلوك المرحلة 1)، وحالة `new` متاحة في الانتقالات. إن أردتها نقطة البداية غيّر حالة الإدراج في `create_order` وسجل التاريخ.
- **صلاحية `orders.view`** تكشف بيانات الاتصال داخل الطلب (لازمة للشحن). صلاحية `customers.view` تتحكم بقسم الزبائن (السجل، الملاحظات، أفراد الأسرة). لا يُحجب الهاتف عمودياً عن من يملك `orders.view` فقط.
- المبيعات في التقارير تُحسب بتاريخ إنشاء الطلب لا تاريخ التسليم.
- لم أبدأ المرحلة 3.
