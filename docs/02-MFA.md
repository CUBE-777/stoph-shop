# التحقق بخطوتين (MFA)

## ما نُفّذ وما اعتُمد
- **آلية Supabase Auth المدمجة (TOTP: تطبيق مصادقة)** — لا آلية مخصصة. السر ورمز QR يولّدهما Supabase؛ الواجهة تعرضهما وترسل الرمز فقط.
- **التكلفة (تحقق من صفحة Supabase الرسمية):** TOTP مدمج بلا إضافة مدفوعة. **Phone/SMS MFA إضافة مدفوعة** (≈ 75$ شهرياً للمشروع الأول) ولم أفعّلها ولن تحتاجها.
- **الفرض في قاعدة البيانات لا في الواجهة:** الدالة `has_permission()` (بوابة كل سياسات RLS وكل الدوال الإدارية) و`my_permissions()` و`is_owner()` تُرجع «لا» إذا كان دور الموظف يتطلب MFA وجلسته بمستوى `aal1`. حتى لو عُدّلت الواجهة لا يُفتح شيء.
- الأدوار الافتراضية المطلوب لها MFA: `owner` (دائماً، لا يمكن إزالتها) و`manager`. `support` وأي دور جديد: بلا إلزام حتى تحدده من **/admin/security**.

## التفعيل الآمن (بالترتيب، لا تقفز)
1. نفّذ `10_phase3_security.sql`. **لا يتغير شيء** (الفرض مُوقَف: `mfa_enforced = false`).
2. ادخل /admin بحساب المالك → **الأمان** → «إضافة تطبيق مصادقة» → امسح QR (Google/Microsoft Authenticator أو Aegis أو 2FAS) → أدخل الرمز.
   **احفظ المفتاح السري النصي** (يظهر أسفل QR) في مدير كلمات مرور: هو وسيلتك الوحيدة لاستعادة التوليد إن ضاع الهاتف.
3. سجّل الخروج ثم الدخول: يجب أن يطلب الرمز.
4. من **الأمان → فرض التحقق** فعّل الفرض (يرفض الخادم التفعيل إن لم تكن جلستك الحالية `aal2`، لحمايتك من قفل نفسك).
5. بعدها يُطلب من كل موظف بدور مُلزَم إعداد التطبيق عند أول دخول (شاشة إلزامية). الموظفون بأدوار غير مُلزَمة لا يتأثرون.
6. وزّع التعليمات على الموظفين الحساسين (مدير، أي دور فيه `staff.manage` أو `reports.view` أو `coupons.manage`) وفعّل الإلزام لأدوارهم.

> ملاحظة من وثائق Supabase: عند التحقق من عامل جديد تُسجَّل الجلسات الأخرى للمستخدم خروجاً.
> وحذف عامل مُفعّل يتطلب جلسة `aal2`.

## فقدان الهاتف (الاسترجاع الآمن)
تحقق من هوية الشخص **بوسيلة خارج النظام** (اتصال مباشر معروف) قبل أي خطوة. بالترتيب من الأسهل:
1. **يملك المفتاح السري المحفوظ:** يضيف التطبيق على الهاتف الجديد بإدخال المفتاح يدوياً (يولّد الرموز نفسها). لا حاجة لتدخل.
2. **موظف فقد الوصول:** المالك يحذف عامل التحقق للموظف من لوحة Supabase (Authentication → Users → المستخدم؛ خيار حذف عوامل MFA إن ظهر في إصدار لوحتك)، أو بـ SQL في SQL Editor (يعمل بصلاحية مالك القاعدة):
   ```sql
   -- غير المعرّف! يحذف كل عوامل التحقق لهذا المستخدم فقط.
   delete from auth.mfa_factors where user_id = '00000000-0000-0000-0000-000000000000';
   ```
   عند الدخول التالي سيُطلب منه إعداد جديد (إن كان فرض MFA مفعّلاً ودوره مُلزَم). *(حذف الصف من `auth.mfa_factors` لم يُجرَّب هنا؛ جرّبه على حساب اختبار أولاً.)*
3. **المالك نفسه فقد كل شيء وليس عنده مفتاح محفوظ:** أوقف الفرض من SQL Editor، ثم احذف عامل المالك كما في (2) وأعد إعداده وفعّل الفرض:
   ```sql
   update public.app_settings set value = 'false', updated_at = now() where key = 'mfa_enforced';
   -- ... احذف عامل المالك، ادخل، أعدّ التطبيق، ثم من /admin/security فعّل الفرض.
   ```
   هذا يعمل لأن SQL Editor يدخل بحساب مالك المشروع في Supabase (وهو بدوره يجب أن يكون محميّاً بـ MFA على حساب Supabase نفسه).
4. سجّل الحادثة (من، متى، كيف تحققت من الهوية). تغييرات `app_settings` والأدوار تظهر في سجل التدقيق عندما تتم عبر التطبيق؛ تغييرات SQL Editor تظهر بلا فاعل.

## قيود صريحة
- لا رموز استرجاع (recovery codes) في Supabase TOTP؛ لذلك المفتاح السري المحفوظ أو مالك آخر هما الاسترجاع.
- يُنصح بوجود **مالكَين** لكل منهما عامل خاص (الحماية من فقدان الوحيد). لا تُشارك حساباً واحداً.
- لم يُجرَّب شيء من هذا على Supabase حقيقي: الاختبار مكتوب (`db_tests_phase3.sql` القسم 6) ويتطلب تشغيلك، وتجربة الشاشات تتطلب متصفحاً.
