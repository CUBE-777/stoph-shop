# مراجعة أمنية — Stoph Shop (المرحلة 3)

> **حدود هذه المراجعة (اقرأها أولاً):** أُجريت بقراءة الكود وملفات SQL كاملة وبفحوص آلية ساكنة (`npm test`).
> **لم يُنفَّذ أي SQL** (لا PostgreSQL في بيئة العمل)، ولم يُبنَ المشروع ولم يُفتح في متصفح، ولم يُشغَّل `npm audit` (لا إنترنت).
> لذلك لا أدّعي أن المشروع «آمن»؛ كل بند أدناه موسوم بحالته الحقيقية. الاختبارات العملية للأدوار مكتوبة في
> `tests/db/db_tests_phase3.sql` وتنتظر تشغيلك لها على مشروع تطوير.

## 1) ما فُحص

| المجال | ما وُجد | الحكم |
|---|---|---|
| سياسات RLS | كل الجداول مفعّل عليها RLS؛ الزائر بلا صلاحية على الطلبات والزبائن والموظفين؛ الكتابة في الطلبات عبر دوال `security definer` فقط | سليم بالقراءة |
| Storage | الحاوية عامة (قراءة بالرابط) والكتابة للموظفين بصلاحية المنتجات؛ حدّ الحجم وأنواع MIME في إعداد الحاوية | عُزّز (F7) |
| المصادقة والجلسات | التسجيل الذاتي يُعطَّل يدوياً؛ لا صلاحيات لغير الموظفين حتى لو سُجّل مستخدم | سليم، يحتاج ضبط لوحة Supabase (انظر 3) |
| الدعوات | دالة `invite-staff` تتحقق من JWT والصلاحية؛ **كانت ترسل البريد قبل فحص قواعد المنح** | أُصلح (F1) |
| إنشاء الطلب والأسعار والكوبونات | الأسعار والخصم والتوصيل تُحسب في `_price_order` على الخادم؛ المتصفح لا يرسل سعراً؛ أقفال `for share/update` | سليم بالقراءة |
| التتبع | رمز 10 خانات hex + الهاتف؛ حجب بعد المحاولات الخاطئة؛ جواب واحد لكل الأخطاء | سليم، مع قيد (F13) |
| تغيير الحالات والأدوار | جدول انتقالات + صلاحية لكل انتقال؛ منع منح النفس؛ حماية آخر مالك | سليم؛ وسُدّ مسار الإلغاء/الإرجاع (F5) |
| التحقق من المدخلات | قيود CHECK في الجداول + تحقق في الدوال + تحقق في الواجهة | سليم |

| الأسرار | لا مفاتيح في الكود؛ المتصفح يستعمل `anon` فقط؛ **`.gitignore` و`.env.example` كانا مفقودين من الأرشيف** | أُصلح (F2) |
| التبعيات | `package.json` بنطاقات `^` و**بلا `package-lock.json`** | مفتوح (F11) |

## 2) النتائج

الخطورة تقديرية. «أُصلح» = عُدّل في الكود/SQL لكن **لم يُختبر على قاعدة حقيقية** ما لم يُذكر غير ذلك.

| # | الخطورة | المشكلة | الحالة |
|---|---|---|---|
| F1 | متوسطة | `invite-staff` ترسل بريد دعوة ثم تفحص قواعد المنح، فيستطيع حامل `staff.manage` غير المالك دفع المشروع لمراسلة عناوين عشوائية | أُصلح: `can_grant_roles()` تُفحص قبل الإرسال + تحقق من صيغة المعرفات |
| F2 | متوسطة | غياب `.gitignore` و`.env.example` رغم اعتماد README عليهما (خطر رفع `.env.local` إلى GitHub) | أُصلح: أُضيفا، و`backups/` و`*.dump` مستثناة |
| F3 | منخفضة | مطابقة المدينة لرسوم التوصيل حرفية (`Fès` ≠ `Fes`) فيُحاسَب الزبون بالسعر الافتراضي خطأً | أُصلح: `city_key()` (حروف صغيرة + إزالة تشكيل الفرنسية + تطبيع الفواصل). **الأسماء العربية لا تُحوَّل**: أضف صفاً لكل تهجئة |
| F4 | منخفضة | «طلبات اليوم» تعتمد يوم UTC، وفلتر التاريخ في الواجهة بإزاحة ثابتة `+01:00` (المغرب يتحول إلى +00 في رمضان) | أُصلح: حساب يوم الدار البيضاء على الخادم (`admin_search_orders`, `admin_dashboard`) |
| F5 | متوسطة | يمكن إلغاء/إرجاع طلب بلا سبب ولا سجل مستقل | أُصلح: `cancel_order` / `register_return` / `update_return` + جدول `order_returns` (لا يُحذف أبداً)، و`set_order_status` يرفض `cancelled/returned` |
| F6 | عالية (غياب ضابط) | لا تحقق متعدد العوامل | نُفّذ TOTP (انظر `02-MFA.md`). **متوقف افتراضياً حتى يفعّله المالك** كي لا يُقفل أحد |
| F7 | منخفضة | سياسة رفع الصور لا تقيّد المسار ولا الامتداد | عُزّزت (مجلد = معرّف منتج موجود + jpg/png/webp) + سياسة SELECT للموظفين. **سلوك Storage API مع هذه السياسات غير مُجرَّب**: جرّب رفع/حذف صورة بعد التطبيق |
| F8 | أداء | `has_permission` تُقيَّم لكل صف | أُصلح للجداول الكبيرة بـ `(select ...)` |
| F9 | أداء | مفاتيح أجنبية بلا فهرس (حذف منتج/كوبون يمسح `order_items`/`orders` تسلسلياً) | أُضيفت 5 فهارس |
| F10 | منخفضة | ترويسات الأمان ناقصة | أُضيفت HSTS وPermissions-Policy وCOOP. **CSP موضوعة Report-Only** لأنها لم تُجرَّب في متصفح؛ فعّلها يدوياً (`05-DEPLOY.md`) |
| F11 | متوسطة | لا `package-lock.json`، فالبناء غير قابل للتكرار ولم يُفحص `npm audit`؛ Vite ^5.4.0 قد يلتقط نسخة قديمة | **مفتوح/يدوي**: نفّذ `npm install` ثم `npm audit` وارفع القفل. أُضيف Dependabot وCI (غير مُجرَّبين) |
| F12 | معلومة | إيقاف موظف يسحب صلاحياته في قاعدة البيانات فوراً (تُفحص كل طلب)، لكن حسابه في Supabase Auth يبقى قادراً على تسجيل الدخول بلا صلاحيات، وجلسته صالحة حتى انتهاء JWT | مقبول؛ لحظر كامل احظره من Authentication → Users |
| F13 | منخفضة | تحديد المعدل حسب IP «بأفضل جهد»، ولا CAPTCHA؛ ومن يعرف هاتفاً يستطيع حجب تتبعه 15 دقيقة | **مفتوح**: أضف Turnstile/CAPTCHA عند ظهور إغراق |
| F14 | منخفضة | عدّاد استعمال الكوبون لا يُعاد عند إلغاء الطلب | **قرار لك**: سلوك حالي موثّق، لم أغيّره |
| F15 | معلومة | `audit_logs` تحوي نسخة صف الزبون (الهاتف) عند التعديل | قيّد `audit.view` للمالك؛ راجع الاحتفاظ بالبيانات الشخصية وفق القانون المغربي (09-08 / CNDP) مع مختص — لست مستشاراً قانونياً |
| F16 | تشغيلية | مشاريع Supabase المجانية **تتوقف بعد أسبوع بلا نشاط** (من صفحة التسعير الرسمية) | **مانع إطلاق محتمل**: متجر حقيقي يحتاج خطة مدفوعة أو نشاطاً منتظماً |
| F17 | منخفضة | كلمة المرور: 10 أحرف تُفحص في الواجهة فقط | اضبط الحد الأدنى وحماية كلمات المرور المسرّبة في Authentication (توفرها حسب خطتك: تحقق) |

## 3) قائمة ضبط يدوي في لوحة Supabase (لا يمكن فرضها من الكود)
1. Authentication → Sign In / Providers: **عطّل** «Allow new users to sign up».
2. Authentication → URL Configuration: ضع رابط موقعك الحقيقي فقط في Site URL وRedirect URLs.
3. Authentication → Multi-Factor: تأكد أن **TOTP** مفعّل (هو المجاني). لا تفعّل Phone (مدفوع).
4. Authentication → Passwords: حدّ أدنى ≥ 10 وفعّل ما تتيحه خطتك.
5. Project Settings → API: انسخ `anon` فقط إلى Netlify. **`service_role` لا يغادر جهازك** (يُستعمل فقط في سكربت النسخ الاحتياطي محلياً).
6. Database → Backups: تحقق مما تتيحه خطتك فعلاً ولا تفترض.

## 4) اختبار الأدوار (زائر / موظف محدود / مدير)
مُغطّى في `tests/db/db_tests.sql` و`db_tests_phase2.sql` و`db_tests_phase3.sql`:
زائر (`anon`) ممنوع من الطلبات والزبائن والمرتجعات والدوال الإدارية؛ `support` يؤكد ولا يلغي ولا يرى التقارير؛
`manager` يلغي ويسجّل الإرجاع لكنه لا يدير الموظفين ولا يغيّر MFA؛ المالك وحده يغيّر الأدوار وفرض MFA.
**كلها لم تُشغَّل بعد** — النتيجة الفعلية تُسجَّل في `06-TEST-REPORT.md` بعد تشغيلك.
